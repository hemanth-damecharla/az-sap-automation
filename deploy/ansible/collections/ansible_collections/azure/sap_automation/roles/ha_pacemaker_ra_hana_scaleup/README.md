# ha_pacemaker_ra_hana_scaleup

Resource agent provider for SAP HANA scale-up with system replication. It
creates the topology and database clones, the virtual IP with its Azure load
balancer probe, the colocation and order constraints, and the resource
defaults. On RHEL 8.2 and later it also orders `pacemaker.service` after the
systemd unit of the SAP HANA instance.

## Prerequisites

A running cluster with fencing, HANA System Replication between the two
nodes, and the HA/DR provider hook. Those are configured outside this role.

## Inputs

See [`meta/argument_specs.yml`](meta/argument_specs.yml). Required:
`ha_pacemaker_ra_hana_scaleup_sid`,
`ha_pacemaker_ra_hana_scaleup_instance_number` and
`ha_pacemaker_ra_hana_scaleup_virtual_ip`.
`ha_pacemaker_ra_hana_scaleup_flavor` selects `classic` (SAPHana) or `angi`
(SAPHanaController with SAPHanaFilesystem).

## HANA file systems on NFS

Set `ha_pacemaker_ra_hana_scaleup_nfs` when `/hana/data`, `/hana/log` and
`/hana/shared` are NFS volumes, such as Azure NetApp Files. What the role adds
follows the Microsoft Learn guides for HANA scale-up with Azure NetApp Files
on RHEL and SLES:

| | classic | angi |
| --- | --- | --- |
| RHEL | Per node, a group `g_hana_<SID>_NFS_<n>` of three `Filesystem` resources (`OCF_CHECK_LEVEL=20`, `on-fail=fence`) that never runs or probes on the other node, an `attribute` resource `attr_hana_<SID>_NFS_<n>_active` started after it, HANA allowed only where an attribute is `true`, and HANA stopped before the file systems | Nothing; the file systems stay in `/etc/fstab` and `SAPHanaFilesystem` checks them |
| SLES | A cloned bind mount `rsc_fs_check_<SID>_HDB<nr>` of `/hana/shared/<SID>/check/` that fails, and fences, when the share is not writable | Nothing; `SAPHanaFilesystem` |

On RHEL with classic, `ha_pacemaker_ra_hana_scaleup_nfs_mounts` lists each
node's volumes, and the file systems must not be in `/etc/fstab`; the
cluster mounts them. The names match those of earlier SDAF releases.

## Platform variables

`vars/main.yml` describes the SAPHanaSR-angi layout on SLES. Platform files
hold differences only and are merged recursively:

| File | Differences |
| --- | --- |
| `Suse.yml` | `ocf:suse` provider; classic uses `Master`/`Slave`, a fencing start operation on the IP, and `target-role` |
| `SLES_SAP_12.yml` (linked as `SLES_12.yml`) | `<master>` element instead of a promotable clone |
| `RedHat.yml` | systemd drop-in for `pacemaker.service`, pcs resource names for classic, probe before IP in the group, priorities, mandatory asymmetric order, 15s priority fencing delay |
| `RedHat_10.yml` | `Promoted`/`Unpromoted` role names |

Resource ids match those created by earlier SDAF releases, so an existing
cluster is adopted. The ids of nested attributes and operations differ from
those generated by `pcs` and `crmsh`, so the first run against such a cluster
rewrites the definitions once and reports `changed`.

## Idempotency and check mode

The desired configuration is compared first. Only when it differs does the
role enter maintenance mode, apply resources and constraints, and leave
maintenance mode. A second run reports no change. Check and diff mode are
supported.

## Rollback

Put the cluster in maintenance mode, then remove the constraints and
resources with `pacemaker_cib state=absent`, using the ids rendered by
`templates/cib/hana.xml.j2`. HANA itself is not stopped by removing
unmanaged resources.

## Status against `roles-sap/5.5-hanadb-pacemaker`

Covers `5.5.4.1-cluster-RedHat.yml` and `5.5.4.1-cluster-Suse.yml` for the
base topology, and `5.5.4.0-clusterPrep-*.yml` with the ANF parts of
`5.5.4.1-cluster-*.yml` for the file system resources. Not yet migrated, and
still served by the legacy role: the active/read-enabled secondary virtual IP, moving the primary back after configuration, RHEL 7,
and everything outside the cluster resources (system replication, hook,
sudoers, post-provision report).

Linted, template-tested for RHEL 9 and 10 and SLES 12, 15 and 16, and run with
real Ansible against stand-ins for the cluster tools. Not yet executed against
a live cluster.
